# План аппаратного опыта

Дата: 2026-10-18. Продолжение [сокращения задержки шага](15%20Задержка%20шага%20и%20параллельные%20системы.md). Плата ожидается; аппаратных обращений при подготовке этого плана не было.

План выполнен после подключения. Первоначальный образ выявил аппаратный отказ маршрута данных DSP; использовать актуальный исправленный образ и результаты из [отчёта опыта](18%20Аппаратный%20опыт%20автономного%20ядра.md). Ниже сохранены исходные ожидания до подключения.

## Готовность

Готовы к первой аппаратной проверке полного автономного ядра и сравнению задержки одной траектории с C на M1. Скорость этой версии на плате ещё не измерена.

Повторно проверен `build/fpga_madness.bit`: контрольная сумма, соответствие исходникам, обработка DSP и временные ограничения подтверждены. SHA256 — `131859947585f7dde7c65c4c64934ba30bd4b4a13737b0f66ea40cdf48e68abf`. Ограничение 80 МГц выполнено с оценкой nextpnr 81.48 МГц. Эта оценка не задаёт частоту генератора.

В сохранённых журналах RTL и схемы после синтеза подтверждены 494 проверки обмена полного ядра. Отдельные проверки умножителей, переходов между тактовыми областями и интегратора описаны в предыдущем документе. Успешное моделирование не заменяет аппаратной проверки исправленных управляющих битов DSP и нового обмена.

Последняя известная конфигурация в FPGA — отдельная диагностика. После выключения питания временная конфигурация могла исчезнуть. Для опыта загружаем полный проверенный образ; наличие DPU2 само по себе не подтверждает точную версию прошивки.

## Порядок первого подключения

Выполнять последовательно, прекращая опыт при ошибке предыдущего этапа:

```sh
set -eu
make doctor
make probe
.venv/bin/python scripts/check_bitstream.py build/fpga_madness.bit
ALLOW_FPGA_PROGRAM=YES make program
make проверить-плату
.venv/bin/python scripts/dpu.py плата --полная-проверка
make проверить-интеграторы
make проверить-автономность
make сравнить-плату
```

Загрузка временной PL выполняется в рамках ранее полученного явного разрешения. `make probe` должен подтвердить BYPASS и повторное чтение IDCODE: одного обнаружения цепочки недостаточно. Команда `make program` повторно проверяет образ и сохраняет предохранитель разрешения. Сырой `_build/default/hardware.bit` для опыта не используется.

Если проверка образа обнаружит изменение исходников, сначала нужны новая сборка `make bitstream` и `make sim-синтез`; для изменённого RTL также `make lint` и `make sim`. Неизменённый подтверждённый образ пересобирать перед подключением не требуется.

Четыре модели загружаются в одну конфигурацию FPGA. Между ними меняются описание графа, параметры и состояния, а не прошивка.

| Этап | Условие успеха |
| --- | --- |
| Четыре модели | Побитное совпадение состояний с целочисленным эталоном, 256 принятых шагов, `done=1`, `fault=0`, точные счётчики |
| Полный набор | 494 проверки обмена: повторные запуски, ошибки конфигурации, переполнения, общая отмена перехода, запрет записи во время расчёта |
| Автономность | Перед паузой `busy=1`; после 300 мс без TCK завершён миллион шагов, принято 4 миллиона тактов, состояние сохранено |
| Частота | Свободный счётчик продвигается без TCK; частота измерена именно в полной конфигурации |
| Сравнение | Новый C-эталон проверен, результаты CPU и FPGA совпали, время расчёта и обмена записано раздельно |

Проверка автономности использует нулевую производную. Она доказывает независимое исполнение и работу счётчиков; производительность содержательных моделей определяется следующим этапом. Если Mac задержал первый опрос до завершения миллиона шагов, отсутствие наблюдённого `busy=1` требует повторного опыта с увеличенным запуском и паузой, а не немедленного вывода об ошибке ядра.

## Что измеряем

### Частота и задержка одной траектории

Источник тактов — `CFGMCLK`; прежняя диагностика дала около 65 МГц. В полном ядре частоту измеряем заново по разности 64-разрядного счётчика за двухсекундную паузу. Сохраняем нижнюю и верхнюю оценки из времени обменов. Они характеризуют способ измерения; температурный дрейф и миллисекундная дискретность часов хоста требуют отдельного учёта при более точном опыте.

| Модель, текущие параметры | Тактов/шаг | Тактов за 256 шагов | Условное время шага при 65 МГц |
| --- | --- | --- | --- |
| Лоренц | 12 | 3072 | 185 нс |
| RLC | 17 | 4352 | 262 нс |
| Тепловая цепочка | 12 | 3072 | 185 нс |
| Осциллятор | 5 | 1280 | 77 нс |

Последний столбец — прогноз. После аппаратной проверки счётчика вычисляем:

```text
время расчёта = измеренное число тактов / измеренная частота
время шага = время расчёта / число принятых шагов
шагов в секунду = число принятых шагов / время расчёта
```

Счётчик расчёта отражает работу после проверки запуска; это не задержка от отправки RUN хостом. На 256 шагах ожидаются десятки микросекунд. Миллисекундные отметки OpenOCD не разрешают такое время непосредственно: время ядра восстанавливаем по его счётчику и частоте, явно указывая этот способ.

### Затраты хоста и JTAG

Существующий сценарий отдельно сохраняет время загрузки модели, RUN с ожиданием и опросом завершения, чтения результатов и всего процесса OpenOCD. Время RUN включает передачу и опрос, поэтому его нельзя подписывать как чистое время решателя. Сумма отдельных обменов не обязана совпасть со временем всего процесса: там также есть запуск OpenOCD и проверка цепочки.

Сравнение выполняется для уже загруженной конфигурации FPGA; время программирования PL не входит в каждый запуск модели. В итогах нужны обе величины: задержка вычисления в ядре и полное время задачи через текущий интерфейс.

### Равные условия для M1

Одна траектория на FPGA сравнивается с одной траекторией в оптимизированном C, один поток CPU. Совпадают граф, параметры, начальные состояния, dt, 256 шагов Эйлера, Q16.16, округление и отказ всего шага при переполнении. В C граф развёрнут в выражения и быстрый путь степенного dt выбирается до цикла.

`make сравнить-плату` заново собирает и проверяет C, затем сохраняет девять временных выборок CPU и их медиану. Исторические времена C из первого сравнения не подставляются вместо нового измерения: после изменения быстрого пути это другая версия программы.

Отношение `время FPGA / время C` больше единицы означает проигрыш FPGA. Выигрыш заранее не предполагается. Если малые графы останутся медленнее, результат опыта — проверенная величина разрыва и стоимость зависимостей одной траектории.

## Что уже автоматизировано и что расширять позже

Первый проход выполняется имеющимися командами. `make сравнить-плату` сохраняет `reports/сравнение-автономное-ядро.json`: параметры машины, компилятор и флаги, контрольные суммы, исходные данные, частоту, выборки CPU и аппаратные ответы. Автономность сохраняется отдельно в `reports/автономность.json` и журналах. Отчёт сравнения создаётся после успешного завершения всех моделей; при сбое нужно сохранить вывод команды, чтобы не принять старый файл за новый результат.

Сейчас аппаратный запуск в сравнении один на модель, частота измеряется один раз, число шагов фиксировано равным 256. Этого достаточно для первой сверки детерминированного числа тактов. Для статистики задержек USB и устойчивости результата нужна отдельная серия: несколько полных повторов с разными именами отчётов и измерением частоты до и после серии. При разбросе частоты следует пересчитать диапазон времени ядра.

Далее полезны два расширения:

- Сопоставить степенной dt и общий тракт умножения на соответствующих C-реализациях. Нестепенные dt уже проверяются функционально, но отдельного сравнения их скорости пока нет. Изменение dt меняет физический горизонт при том же числе шагов; сравнение стоимости шага не является сравнением точности на одном физическом интервале.
- Проверить короткие и длинные запуски, отделив постоянные затраты загрузки от расчёта. Нельзя без проверки запускать миллионы шагов любого из четырёх примеров: явный Эйлер, округление и переполнения меняют поведение длинной траектории. Для каждого случая нужны эталон и проверка числа реально принятых шагов.

Большие связанные графы и чередование независимых систем ещё не реализованы. Этот опыт измеряет задержку одной малой траектории; будущая проверка суммарной пропускной способности потребует новой реализации и векторизованного CPU-эталона. Потребление энергии текущие сценарии не измеряют.
