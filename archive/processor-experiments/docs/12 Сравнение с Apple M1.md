# Сравнение с Apple M1

Дата: 2026-10-17. Первый опыт для четырёх моделей из [описания ядра](11%20Первое%20ядро.md). Одна траектория, 256 шагов, один поток CPU. В этом опыте M1 быстрее первого ядра даже при исключении затрат JTAG.

Это сравнение с функциональным образцом на внешнем TCK, без DSP и без оптимизации под высокую рабочую частоту. Разбор причин отставания и план исправления находятся в [документе о тактировании](13%20Тактирование%20и%20ограничения%20первого%20образца.md). Полученные отношения не следует переносить на будущую оптимизированную реализацию.

Текущие исходники уже относятся ко [второму ядру](14%20Второе%20ядро.md). Команды сравнения используют его протокол и задержки; новый отчёт — `reports/сравнение-автономное-ядро.json`. Исторический `reports/сравнение.json` сохранён. Новое аппаратное сравнение выполнено 2026-10-18 и описано в [опыте автономного ядра](18%20Аппаратный%20опыт%20автономного%20ядра.md).

## Одинаковая задача

Сравниваются те же графы, параметры, начальные состояния, dt и число шагов. Обе стороны используют явный Эйлер и знаковую Q16.16. После каждого узла проверяется диапазон 32 бит. Произведение округляется вниз после деления на 65536, включая отрицательные значения. Все пробные состояния проверяются перед общей записью; при переполнении сохраняется последний принятый шаг.

На CPU не запускается интерпретатор графа. `scripts/benchmark.py` разворачивает описания из `scripts/dpu.py` в четыре функции C с обычными выражениями. Получается один исполняемый файл с четырьмя решателями. Начальные состояния, параметры, dt и число шагов поступают через аргументы программы, поэтому компилятор не знает их значения. Выбор модели выполняется до цикла шагов. Компилятору разрешены обычные оптимизации, сохраняющие результат.

Подготовка графа и компиляция C не входят во время расчёта CPU. Загрузка графа FPGA также исключена из времени по тактам и приведена отдельно. Для следующего сравнения при равной допустимой физической ошибке следует дополнительно исследовать `float`, `double` и другие методы; нынешний опыт сравнивает точную семантику первого аппаратного профиля.

## Условия измерения CPU

| Показатель | Значение |
| --- | --- |
| Компьютер | MacBook Air `MacBookAir10,1` |
| Процессор | Apple M1, 8 логических процессоров |
| Память | 16 ГиБ |
| ОС | macOS 15.7.4, arm64 |
| Компилятор | Apple clang 17.0.0, `clang-1700.4.4.1` |
| Оптимизация | `-std=c11 -O3 -mcpu=native -fno-lto` |
| Потоки | Один, выбор ядра оставлен планировщику macOS |
| Часы | `clock_gettime(CLOCK_MONOTONIC_RAW)` |

Каждый повтор начинает новую траекторию из одинакового начального состояния. В измерение входят вызов функции, инициализация её состояний, 256 шагов, возврат результата и его вклад в контрольную сумму. Доступа к Python или JTAG внутри этого цикла нет. Несколько траекторий одновременно не вычисляются.

Перед измерением выполняются 64 прогревочных запуска. Число повторов удваивается, пока пробная серия не займёт хотя бы 30 мс. Затем измеряются девять серий; в итоговой таблице используется медиана времени одной траектории. Первые три модели получили по 16384 повтора в серии, осциллятор — 32768. Время на шаг — время траектории, делённое на 256, а не отдельное измерение каждого шага.

Решатели и цикл измерения компилируются в отдельных единицах трансляции без LTO — оптимизации при компоновке. Это не позволяет вынести одинаковый вызов решателя из цикла повторов. Результаты участвуют в контрольной сумме с наблюдаемой записью. При просмотре ассемблерного вывода подтверждён вызов функции внутри измеряемого цикла.

Частота CPU не фиксировалась, привязки к производительному ядру и измерения энергии нет. Диапазон девяти серий отражает разброс этого запуска, а не доверительный интервал для всех условий эксплуатации.

## Результаты вычислений

FPGA использует прежнюю конфигурацию на 9 узлов без DSP. Частота TCK настроена на 1 МГц. Столбец FPGA ниже вычислен как `аппаратные такты / 1 МГц`: он предполагает непрерывную выдачу TCK и исключает все паузы USB. Это расчётная оценка, а не измерение реального времени сигнала `busy`.

| Модель | C, нс/шаг, медиана | C, диапазон серий, нс/шаг | FPGA, тактов/шаг | FPGA при непрерывных 1 МГц, нс/шаг | Отношение FPGA/C |
| --- | --- | --- | --- | --- | --- |
| Лоренц | 10.47 | 10.41–10.77 | 5 | 5000 | 477 |
| RLC | 8.50 | 8.38–8.65 | 6 | 6000 | 706 |
| Тепловая цепочка | 10.26 | 10.18–10.82 | 5 | 5000 | 488 |
| Осциллятор | 3.72 | 3.69–3.75 | 3 | 3000 | 806 |

Время CPU на всю траекторию: 2.682, 2.175, 2.625 и 0.953 мкс соответственно. Время FPGA по тактам: 1280, 1536, 1280 и 768 мкс. Значение отношения больше единицы означает преимущество CPU.

Побитовая проверка C выполнена в 232 случаях: по 116 для обычной сборки и сборки с обнаружением неопределённого поведения (`-fsanitize=undefined -fno-sanitize-recover=all`). Для каждой модели проверены 0, 1, 16, 256 и 1024 шага, затем 24 набора изменённых знаковых состояний, параметров и dt. Начальное значение генератора — 20261017. Проверяются конечные состояния, число принятых шагов и отказ при переполнении. Эталон — целочисленная модель Python, ранее сопоставленная с FPGA и независимыми физическими уравнениями.

## Измерение JTAG на плате

Каждая модель была загружена и запущена в уже настроенной FPGA. Проверены ответы управления, идентификатор ядра, завершение без ошибки, 256 принятых шагов, число тактов и конечные состояния. Все четыре результата совпали побитно с C и Python. Выполнено 104 обмена; FPGA между моделями не перепрограммировалась.

В каждом случае использовалась новая сессия OpenOCD. Обратное чтение каждой записи конфигурации в этом измерении не выполняется; ответы на записи и конечные результаты проверяются. Полный функциональный набор из 393 проверок остаётся отдельным испытанием.

| Модель | Загрузка графа и состояния с подтверждениями, мс | Вызов `runtest`, мс | Запрос RUN вместе с ответом, мс | Чтение статуса, счётчиков и состояний, мс | Весь процесс OpenOCD, мс |
| --- | --- | --- | --- | --- | --- |
| Лоренц | 179 | 87 | 93 | 48 | 444 |
| RLC | 145 | 114 | 120 | 40 | 409 |
| Тепловая цепочка | 185 | 86 | 92 | 56 | 440 |
| Осциллятор | 88 | 52 | 58 | 40 | 289 |

Это по одному наблюдению для каждой модели в итоговом запуске. Время частей измерено командой OpenOCD `ms`, разрешение — 1 мс. Полное время процесса измерено Python `perf_counter`; оно включает запуск OpenOCD, инициализацию адаптера, проверку BYPASS/IDCODE и завершение процесса. Подготовка Python и вычисление эталона в него не входят. Вызов `runtest` вложен в обмен RUN; эти два столбца нельзя складывать. Отдельное чтение идентификатора также входит в полное время.

На `runtest` подаются `256 * тактов_на_шаг + 8` импульсов. Настройка 1 МГц не означает миллион импульсов в секунду в среднем с учётом USB. На выдачу пакета уходит 52–114 мс, значительно больше номинальных 0.776–1.544 мс. Измерение включает обслуживание команды адаптером и паузы. Оно не даёт точной длительности `busy`: часть тактов выдаётся при сдвиге JTAG, а пакет имеет небольшой запас. При отсутствии TCK расчёт действительно останавливается.

## Что следует из опыта

Для этих четырёх малых систем выигрыш в задержке одной траектории не получен. Это относится к нынешней реализации: 4 состояния, 9 узлов, явный Эйлер, Q16.16, арифметика без DSP, тактирование через JTAG. Одного увеличения числа шагов недостаточно: CPU уже быстрее на шаге.

Даже если условно подставить оценку nextpnr 24.15 МГц при неизменном числе тактов, отставание по времени вычислений составит примерно 20–33 раза. Это только арифметическая экстраполяция, не результат работы платы на 24.15 МГц. Для равенства с измеренным CPU при нынешних 3–6 тактах потребовалось бы примерно 477–806 МГц. Простое ускорение транспорта такой разрыв не устранит.

Сборка задавала ограничение 1 МГц. Оценка 24.15 МГц для этого размещения не устанавливает предел частоты кристалла или результата будущей оптимизации.

Следующий аппаратный опыт должен обеспечить независимое тактирование и исправную арифметику DSP. Дальнейший архитектурный опыт — определить, при каком размере связанной системы пространственное исполнение окупает частоту и сеть. Для этого нужны более крупные графы, оценка их размещения и отдельный случай со множеством траекторий с учётом векторизации CPU. Добавление ячеек без измерения цены связей пока не обосновано.

Результат этого опыта не определяет скорость будущей архитектуры, максимальную пропускную способность, энергопотребление или цену программируемости относительно специализированной схемы FPGA. Эти вопросы остаются открытыми.

## Воспроизведение

Только измерение CPU и сопоставление с известным числом тактов:

```sh
make сравнить
```

С уже загруженной конфигурацией и разрешёнными записями моделей в наше ядро:

```sh
make сравнить-плату
```

Обе команды сохраняют исходные измерения, параметры моделей, сведения о компьютере, настройки компилятора, контрольные суммы и вывод программ в `reports/сравнение.json`. Повторный запуск перезаписывает отчёт; другой путь можно задать через `.venv/bin/python scripts/benchmark.py --отчёт reports/другой.json`. Созданный C, объектные файлы и программа находятся в `build/benchmark/`. Созданные файлы не сохраняются в Git. Для новой сессии сначала требуется загрузить прежнюю прошивку по порядку из документа о первом ядре.

SHA256 местного файла ранее загруженной прошивки: `f57f436c24fd012af8506e76ff0df88c97e5e4cadc6fbd5e4cd51f37a9d78efe`; чтение всей конфигурации из FPGA для подтверждения этой суммы не выполнялось.
