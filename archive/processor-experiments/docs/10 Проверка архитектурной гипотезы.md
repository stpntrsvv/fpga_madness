# Проверка архитектурной гипотезы

Дата: 2026-10-17. План исследования до подключения платы и последующих аппаратных измерений. Исходное предложение описано в [архитектуре машины состояний](09%20Архитектура%20машины%20состояний.md).

Выполнена первая реализация с программируемыми узлами и проверками в моделировании. Её профиль, численные ограничения и команды находятся в документе [«Первое ядро»](11%20Первое%20ядро.md). План ниже сохраняет дальнейшие исследования, включая ограниченную сеть, альтернативные методы и сравнение с CPU.

Первое сравнение малых моделей с оптимизированным C выполнено на Apple M1: [методика и результаты](12%20Сравнение%20с%20Apple%20M1.md). Нынешний профиль уступает CPU; сравнение более крупных систем и методов при одинаковой допустимой ошибке остаётся частью плана.

## 1. Проверяемый вопрос

Может ли фиксированное ядро с загружаемым графом производных и собственными состояниями сохранить существенную часть преимуществ пространственной аппаратуры под конкретную модель?

У вопроса две независимые части: цена программируемости относительно специализированной схемы и полезность получившейся машины относительно хорошего программного решения на CPU. Успех по одной части не заменяет другую.

Для начала не требуется плата. Она понадобится для проверки загрузки, реальной частоты, обмена и времени исполнения. До этого можно проверить семантику эпох, численные ошибки, вместимость и предполагаемое число тактов.

## 2. Сначала модели и численные требования

Подготовить Лоренца, RLC и семейство тепловых сетей или цепочек масс и пружин. Для каждого случая явно записать уравнения, параметры, начальные условия, внешние воздействия, модельный интервал и допустимую ошибку. Затем рассмотреть конкретную модель PMSM и проверить требуемые нелинейные функции.

Нужны три уровня сравнения:

- эталон с более строгой численной точностью для оценки физического результата;
- программный расчёт с выбранным методом, форматом и точным порядком округлений для проверки семантики аппаратуры;
- оптимизированный расчёт на CPU, достигающий той же допустимой ошибки, для сравнения скорости.

Побитовое совпадение с первым уровнем не требуется. Побитовое совпадение со вторым ожидается там, где правила арифметики полностью определены. Отдельно учитывается ошибка метода интегрирования.

## 3. Модель машины до RTL

Создать исполняемую модель графа и эпох на хосте. Она должна описывать реальные ограничения будущего ядра: типы ячеек, маршруты, задержки, ёмкости промежуточной памяти и число портов. Мгновенная доставка любого значения в любой узел дала бы недостоверную оценку.

Для каждой модели получать:

- число и типы операций, общих выражений и выходов;
- критический путь производных;
- число состояний, связей, рассылок и редукций;
- потребность в регистрах, памяти конфигурации и промежуточных значений;
- размещение, маршруты, расписание и ожидаемое число тактов;
- причину отказа, если модель не помещается.

В этой точке сравнить небольшой постоянный пространственный граф и вариант локального повторного использования ячеек. Первым реализовать тот минимальный пространственный вариант, который позволяет проверить несколько разных моделей.

## 4. Минимальное RTL-ядро

Предварительное разбиение по обязанностям:

| Область | Обязанность |
| --- | --- |
| Хранилище состояний | Текущая и пробная версии, начальная загрузка, смена ролей |
| Вычислительная ячейка | Постоянная конфигурация операции и входов, данные и готовность |
| Сеть связей | Разрешённые маршруты, задержки и рассылки |
| Выходы производных | Полнота вкладов и готовность каждого результата |
| Переход состояния | Выбранный арифметический профиль и поддерживаемый метод |
| Контроллер эпох | Запуск, завершение, проверка ошибок и принятие шага |
| Загрузчик | Проверка совместимости и активация образа при остановке |
| Наблюдения | Снимки принятого состояния и заполнение буфера |

Это обязанности, а не утверждённые имена модулей или границы конвейеров. Конкретное разбиение уточняется после модели ресурсов.

Загрузка выполняется через испытательный интерфейс. Два разных образа модели последовательно загружаются в один экземпляр ядра без смены параметров RTL, повторной компиляции или замены содержимого ROM при сборке. Только такая проверка демонстрирует программирование уже построенной машины.

## 5. Проверки, которые ловят архитектурные ошибки

1. Взаимозависимые состояния: новое значение одного не должно попасть в производную другого в текущей эпохе.
2. Ветви разной задержки и рассылка: все потребители получают значения одной эпохи.
3. Несколько вкладов в производную: ни один не потерян и не учтён дважды; порядок суммы определён.
4. Нулевая производная и состояние без взаимодействий: шаг завершается без ожидания несуществующего сообщения.
5. Переполнение в последнем обновляемом состоянии: ни одно пробное значение не становится принятым.
6. Последовательные запуски и смена модели: признаки готовности и промежуточные значения прошлого запуска не влияют на новый.
7. Неподдерживаемая операция, неверный идентификатор, цикл и нехватка маршрутов: образ отклоняется до запуска.
8. Запуск N шагов без обращений хоста: число принятых шагов и финальное состояние совпадают с программным расчётом.
9. Заполнение буфера наблюдений: остановка происходит на определённой границе, финальный снимок остаётся согласованным.
10. При добавлении многоэтапного метода: промежуточный снимок не перезаписывает исходный, стадии используют правильное время и воздействие.

Для изменений RTL выполняются предписанные репозиторием проверки. Испытания не требуют загрузки FPGA.

## 6. Синтез и цена программируемости

На одном кристалле и с одинаковой арифметикой сравнить:

- схему под фиксированную модель с постоянными связями;
- фиксированное программируемое ядро с той же загруженной моделью;
- при необходимости вариант того же ядра с локальными контекстами.

Для изменяемых параметров специализированная схема тоже должна получать параметры как данные. Иначе её дополнительная оптимизация констант смешается с ценой программируемости графа. Отдельный вариант с полностью постоянными коэффициентами допустим, если это явно отмечено.

Записать LUT, триггеры, DSP, BRAM, частоту после размещения и трассировки, число тактов на шаг и максимальную вместимость. Оценка после одного логического синтеза не заменяет проверку временных ограничений.

Можно измерять долю сохранённой скорости как отношение скорости программируемого ядра к скорости схемы под модель при одинаковой задаче и ошибке. Этот показатель рассматривается вместе с площадью: большее универсальное ядро не получает бесплатный дополнительный бюджет ресурсов.

## 7. Сравнение с CPU

Использовать оптимизированную реализацию без искусственной отправки состояний через внешние интерфейсы на каждом шаге. Указать процессор, компилятор, настройки оптимизации, число потоков, формат, метод и способ измерения. Для нескольких независимых траекторий учитывать векторизацию и параллельное исполнение CPU.

Отдельно измерять:

- задержку одной траектории;
- скорость семейства независимых траекторий;
- скорость большой связанной системы;
- время подготовки и загрузки новой модели;
- время расчёта внутри ядра;
- время получения результата и наблюдений.

Для одного запуска:

```text
T_DPU = T_prepare + T_load + N * T_step + T_read
```

При повторных запусках одной модели подготовка и часть загрузки могут амортизироваться; это явно указывается. Если CPU быстрее на шаге, увеличение N само по себе не создаст преимущества DPU. Если DPU быстрее, определить число шагов, после которого выигрыш перекрывает дополнительные начальные затраты.

Не назначать целевой коэффициент ускорения до первых измерений. Для пользователя существенны и абсолютное время, и область размеров моделей, где преимущество воспроизводится.

## 8. Условия пересмотра

| Наблюдение | Что пересмотреть |
| --- | --- |
| Сеть занимает основную площадь или ограничивает частоту | Локальность размещения, группы ячеек, специализированные пути рассылки и редукции |
| Ячейки большую часть эпохи простаивают | Локальные контексты, несколько независимых экземпляров; отдельно оценить потерю задержки |
| Доминирует чтение состояний | Разбиение банков, регистровые выходы, рассылку и репликацию |
| Численный метод требует слишком малого dt | Метод, арифметику и область применимости |
| Модель не помещается по нелинейным операциям | Набор заранее синтезированных функций и их стоимость |
| Выигрыш возникает только у нескольких независимых моделей | Так и описать область пользы; ускорение одной траектории не заявлять |
| От хорошего CPU отстают все выбранные случаи | Проверить оценки и пересмотреть архитектуру или исследуемый класс задач |

Цель этапа — получить проверяемое объяснение результата, включая отрицательный. Наличие необычной модели исполнения само по себе не является результатом испытания производительности.
